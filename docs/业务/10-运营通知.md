# 10. 运营通知（飞书）

> 本文档基于当前源码状态维护，描述**已实现**的行为。改动通知相关功能时，必须同步更新本文。

## 作用

把「谁注册了」「谁提交了练习」这类运营事件合并推送飞书，省掉翻数据库。面向运营者，用户侧无感知。

## 事件与触发点

| 事件 | 触发点 | 携带内容 |
| --- | --- | --- |
| `user_registered` | `POST /api/auth/login` 新建用户分支（老用户重登不发） | 昵称、脱敏手机号、userId |
| `attempt_submitted` | `_save_attempt_and_review` 收口（同步 `/api/correct` 与流式 `/api/correct/stream` 共用），即一次录音提交完成评估 | 昵称、模式（场景/自由说）、题目、轮次 |

`sourceType=ai_test` 的测试号不入队；通知相关异常只记日志，绝不影响登录与评估主流程。

## 合并窗口

- 队列落 Mongo `notificationEvents`（pending），lifespan 起的后台 flusher 每 `NOTIFY_FLUSH_INTERVAL_SECONDS`（默认 30s）检查一次。
- **第一条立即发**；窗口内（`NOTIFY_WINDOW_SECONDS`，默认 600s）的后续事件攒着，窗口结束后合并成一条发出。
- 结果：每 10 分钟最多一条消息，首条不延迟。
- 发送失败保留 pending 下一轮重试，累计 5 次后标 `failed` 不再重试；日志与 `lastError` 都会抹掉 app_secret。

## 消息形态

```
【SpeakUp】09-18 21:36 动态
新注册 1 人
· 验证用户 · 138****1234 · 21:36
练习提交 1 次
· 验证用户 · 场景「咖啡店给错咖啡」 · 第 1 轮 · 21:36
```

手机号脱敏；每类最多列 8 条明细，其余折叠为「…还有 N 条」；时间按北京时间渲染。

## 配置

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `NOTIFY_ENABLED` | `false` | 总开关；关闭或未配齐应用凭据时全链路 no-op |
| `NOTIFY_FEISHU_APP_ID` / `NOTIFY_FEISHU_APP_SECRET` | 空 | 飞书自建应用凭据，值只存 Infisical `speakup/prod/notifications` |
| `NOTIFY_FEISHU_CHAT_ID` | 空 | 接收群 `oc_...`（生产为「SpeakUp 运营」群） |
| `NOTIFY_FEISHU_BASE_URL` | `https://open.feishu.cn` | 飞书开放平台地址 |
| `NOTIFY_WINDOW_SECONDS` | `600` | 合并窗口 |
| `NOTIFY_FLUSH_INTERVAL_SECONDS` | `30` | flusher 轮询间隔 |

## 发送通道

走飞书 Open API：`POST /open-apis/auth/v3/tenant_access_token/internal` 用 app 凭据换 token（进程内缓存，剩余不足 5 分钟重取），再 `POST /open-apis/im/v1/messages` 以 `chat_id` 发文本消息。token 与消息接口都同时检查 HTTP 状态与响应体 `code`，任一层失败都按发送失败重试。

## 数据

`notificationEvents`（待发/已发/失败事件）与 `notificationState`（`_id=feishu` 记录 `lastSentAt`），字段见 [design/schema.md](../design/schema.md)。

## 前端文件索引

无前端；发送实现在 `server/services/notifier.py`。
