# 渐进式场景提示实施规格

> 状态：已设计
>
> 文档分支：`docs-progressive-scenario-hints`
>
> 基线：`master@8772872`
>
> 目的：让后续 Coding Agent 不依赖聊天上下文，也能完成实现、试点题生成、上线和验收。

## 1. 一句话目标

把场景题从“先给可逐句翻译的中文台词”改成“先理解场景并尝试直接组织英文，确实需要时再逐条索取中文提示”，同时完全保留旧题行为。

## 2. 用户问题与产品判断

### 2.1 当前问题

当前题卡同时展示图片、场景和 `points`。生成提示又明确要求 `points` 是“用户可以直接照着说的中文话”，因此用户很容易先在中文里得到完整表达，再逐句翻译成英文。这练到的是翻译，而不是在场景中直接组织英语。

### 2.2 不采用纯图片

纯图片通常只能表达地点、人物和可见动作，不能稳定表达角色关系、冲突原因、任务边界和成功条件。图片不清楚时，用户会把精力花在猜题，而不是说英语。

因此初始信息保留三层：

1. 图片或现有媒体：快速建立情境。
2. 必要场景：只补图片无法可靠传达的事实。
3. 宽泛目标：说明这次沟通要达成什么，不给可逐句翻译的台词。

可直接借用的中文表达不再默认展示，只在用户主动请求时逐条出现。

### 2.3 学习假设

延迟展示中文提示，会增加用户在没有中文脚本时直接组织英语的机会；按需提示又能避免题意不清或一时卡住导致放弃。

这只是需要用试点数据验证的产品假设，不能因为功能按规格上线就宣称学习效果已经成立。本文分别定义“交付成功”和“试点成功”。

## 3. 后续 Agent 的执行规则

- 本文“已确认决策”“数据与行为契约”“交付验收”是实现边界，不得自行改成另一套产品方案。
- 可以按仓库现有模式调整内部函数、组件和路由命名，但外部行为、兼容规则和验收结果不得改变。
- 开始编码前必须重新核对相关文件的当前实现；本文中的文件名是定位线索，不替代代码调查。
- 若代码现状与本文冲突，或必须改变已确认行为才能完成，应停止并把冲突写清楚，不能静默降级。
- 不得顺手重构无关模块，不得迁移或改写旧题。
- 实现、题目生成、生产投放和线上验收应分阶段进行；任一阶段失败时，不得用后续阶段掩盖。

## 4. 已确认决策

### 4.1 交互与兼容

- 不提供“标准/渐进”用户开关，不保存模式偏好。
- 场景新增独立字段 `interactionType`，不复用现有 `kind`。
- 合法值为 `standard` 和 `progressive_hints`。
- 历史数据缺少 `interactionType` 时一律按 `standard`。
- 旧题不迁移，旧题的展示、评分、抽题和历史行为保持不变。
- 只新生成一批 `progressive_hints` 试点题。
- 试点题覆盖 `task`、`chat`、`describe`、`opinion`、`explain` 五种 `kind`，进入所有用户的正常公共题库。

### 4.2 初始题卡

`progressive_hints` 题首次展示时只显示：

- 现有图片/视频媒体；
- `where`；
- 必要且简短的 `story`；
- 宽泛的 `mission`。

首次作答完成前不得自动显示：

- `points`；
- 尚未请求的 `hints`；
- 标准英文答案；
- 标准答案的变体、关键词列表或双语对照。

### 4.3 逐条提示

- 用户每次主动点击，只新增显示下一条提示。
- 已显示提示累计保留，不用新提示替换旧提示。
- 提示按数组顺序展示，不能随机、跳号或一次展开全部。
- 每条提示是自然、完整的中文句子，不含英文答案或中英对照。
- 用完所有提示后不再增加计数；按钮可隐藏或进入明确的“已显示全部”状态，不得看似仍可点击。
- 同一 Practice Session 内重说时，已经看过的提示继续可见，不能伪装成未看过。
- 页面刷新后仍恢复该 Session 已显示的提示数量。

按钮的具体短文案可遵循现有中英文 i18n 风格；首个动作应表达“给我一点提示”，后续动作应表达“再给一点提示”。文案差异不是另起一套交互的理由。

### 4.4 提示、评分点与分数

- `hints[]` 是展示契约；`points[]` 是评分契约，两者不得继续共用同一字段。
- `task` 题可以有必须完成的信息点：
  - `points` 保存评分需要检查的必要信息；
  - `hints` 与 `points` 一一对应，但写成自然中文提示；
  - 是否点击提示不改变这些必要信息本身。
- 其他四种 `kind` 的渐进提示只帮助展开内容，不是硬性扣分项：
  - 试点题的 `points` 为空；
  - `hints` 不得进入纠错 Prompt 的“必须说到”部分。
- `hintCount` 只用于评估交互，不参与分数、Prompt 或反馈文案。
- 结果页、历史页和分享页不显示“使用了提示”“受帮助”等标签。

### 4.5 指定题目 URL

- 每道试点题必须有稳定且唯一的 `slug`。
- 生产入口固定为 `https://speakup.a4.fit/practice?scenario=<slug>`。
- 该入口复用正常练习流程，不是只读 preview：
  - 登录和权限规则与普通练习一致；
  - 打开后精确选择该题，不随机换成其他题；
  - 用户点击正常的开始动作后创建真实 Practice Session；
  - 作答后正常产生 Attempt、历史、评分和提示计数。
- slug 不存在、题目已归档或用户无权访问时，显示明确的不可用状态；不得静默改抽随机题。
- 开始练习后进入现有规范 Session URL，避免刷新时重复创建 Session。

### 4.6 回退

- 每道试点题都能单独把 `status` 改为 `archived`。
- `archived` 后既不再被正常抽题，也不能通过 slug 链接新建练习。
- 创建 Practice Session 时必须在服务端重新校验题目仍为 `active`，且是公共题或属于当前用户；不能信任此前 slug 查询结果或客户端传入的 `scenarioId`。
- 用户已选题但尚未点击开始时题目被归档，开始请求必须失败；归档前已经创建的 Session 继续可用。
- 回退题目不需要删除历史 Session；已有历史继续依靠快照可读。
- 回退不依赖重新发前端版本：当所有试点题归档后，渐进交互自然停止产生新流量。

## 5. 非目标

- 不做纯图片题。
- 不让 AI 自动判断何时弹提示。
- 不让用户选择或记住一种练习模式。
- 不把旧题批量转换成渐进题。
- 不改变旧 `standard` 题的 `points` 展示或评分语义。
- 不在作答前提供完整英文范文。
- 不因使用提示扣分、改评分权重或生成羞辱性反馈。
- 不建设通用 A/B 平台。
- 不在本轮扩写整套公共题库；试点范围固定为 10 道。

## 6. 数据契约

### 6.1 Scenario

```json
{
  "interactionType": "progressive_hints",
  "kind": "task",
  "points": [
    "指出收到的饮品与订单不符",
    "请求店员重新制作热饮"
  ],
  "hints": [
    "我点的是热拿铁，但这杯是冰的。",
    "能麻烦你帮我重新做一杯热的吗？"
  ]
}
```

规则：

| 字段 | `standard` | `progressive_hints` |
|---|---|---|
| `interactionType` | 可缺省；缺省按 `standard` | 必须显式为 `progressive_hints` |
| `hints` | 可缺省，UI 不使用 | 必须是 2–3 条有序、非空中文字符串 |
| `points` | 保持现有语义 | `task` 为 2–3 条必要信息且与 hints 一一对应；其他 kind 为空数组 |
| `status` | 保持现有语义 | 试点投放为 `active`，回退改为 `archived` |
| `slug` | 保持现有语义 | 必须非空、唯一、可安全放入 URL |

兼容规则：

- 新写入若 `interactionType` 为未知值，应校验失败，不能把拼写错误写进生产。
- 读取历史数据时，缺失或未知值不得触发渐进 UI，应安全按 `standard` 展示并记录可诊断错误。
- API 返回 `interactionType` 时要做缺省归一化，前端不应在多处重复猜测。
- `/api/scenarios/next` 和按 slug 精确读取都要返回 `difficulty`、归一化后的 `interactionType` 以及 `hints`；standard 缺失 hints 时返回空数组。

### 6.2 Practice Session 快照

创建 Session 时，`scenario` 快照必须增加：

```json
{
  "interactionType": "progressive_hints",
  "hints": ["...", "..."],
  "difficulty": 2
}
```

Practice Session 本身保存：

```json
{
  "revealedHintCount": 0,
  "creationRequestId": "8dc6753a-9502-4d69-9722-550e28917846"
}
```

规则：

- `revealedHintCount` 表示已经展示的不同提示数量，不是超过上限后的无效点击数。
- 初始值为 `0`，范围始终为 `0..len(hints)`。
- `difficulty` 随 Scenario 一起快照，供同难度试点分析；旧 Session 缺失时保持可读。
- `creationRequestId` 是开始动作的幂等键；旧客户端可缺省且不得写空字符串，新版开始动作必须提供。
- standard/free Session 缺少 `revealedHintCount` 时按 `0`；历史 Session 缺少 `creationRequestId` 时不补造幂等事实。
- 场景以后被编辑或归档，也不能改变既有 Session 的快照和已显示状态。

### 6.3 Attempt

每个新 Attempt 保存：

```json
{
  "hintCount": 1
}
```

规则：

- `hintCount` 在服务端 reserve Attempt 时，从 Session 当前 `revealedHintCount` 复制。
- 同一 Session 的后续 Attempt 记录当时累计可见的提示数。
- standard/free Attempt 缺省或写 `0`。
- 客户端不能提交任意数字覆盖服务端事实。
- `hintCount` 不传入 corrector，不写入评分 Prompt，不影响 score、gaps、summary 或 standard answer。

## 7. API 与状态流

以下 HTTP 路由、状态码和响应字段是外部契约；内部函数和组件名可按仓库惯例调整。

### 7.1 按 slug 精确取题

新增精确读取能力：

```http
GET /api/scenarios/by-slug/{slug}
```

- 身份只取当前 Bearer token，不把 query/body 中的 `userId` 当身份凭证。
- slug 使用小写 kebab-case：`[a-z0-9]+(?:-[a-z0-9]+)*`，区分大小写，不做猜测性改写。
- 返回字段与现有 `/api/scenarios/next` 的场景部分保持一致，并增加归一化后的 `interactionType` 和 `hints`。
- 只返回 `status=active` 且当前用户可访问的公共题或自有题。
- 不得读取其他用户的定制题。
- 不存在、已归档、slug 非法和无权访问统一返回 `404`，响应为现有 FastAPI 错误结构 `{"detail":"场景不存在或不可用"}`，避免泄露其他用户题目。
- 任何失败都不能回退为随机题。

前端 `/practice?scenario=<slug>`：

1. 精确读取 slug 对应题目。
2. 显示与普通抽题相同的待开始界面。
3. 点击开始时生成一个 UUID `requestId`，随现有创建 Session API 提交。
4. 创建成功后 `replace` 到 `/practice/<practiceId>`。
5. 一个开始动作只创建一个 Session；React 重渲染、超时重试或重复提交同一 `requestId` 时，服务端返回同一个 Session。

创建 Session 的补充契约：

- `requestId` 对新版前端必填；旧客户端未传时保持兼容，但不获得幂等保证。
- Session 保存 `creationRequestId`，并以仅覆盖非空字符串的 `(userId, creationRequestId)` 唯一部分索引或等价机制去重。
- 同一用户重复提交同一 `requestId` 时返回首次创建的完整 Session，状态码仍为 `200`，不得再写一条历史。
- 服务端在写入前重新校验 Scenario 为 `active` 且当前用户可访问；不存在、已归档或越权统一返回 `404`，不产生 Session。
- 同一 `requestId` 若被用于不同创建参数，返回 `409`，不能复用旧 Session 假装成功。

### 7.2 显示下一条提示

新增由服务端持久化的原子动作：

```http
POST /api/practice-sessions/{practiceId}/hints/next
Content-Type: application/json

{"requestId":"22665703-b2c2-4165-b784-f12db479fea3"}
```

成功或同一请求重试时响应：

```json
{
  "requestId": "22665703-b2c2-4165-b784-f12db479fea3",
  "revealedHintCount": 2,
  "hintIndex": 1,
  "hint": "能麻烦你帮我重新做一杯热的吗？",
  "exhausted": true
}
```

语义：

- 校验 Session 属于当前登录用户，且快照为 `progressive_hints`。
- 每次按钮动作生成新的 UUID `requestId`；网络重试必须复用原 requestId。
- Session 保存已处理 reveal requestId 与对应 hintIndex；同一 requestId 重试返回首次的完全相同结果，不再次增加计数。
- 新 requestId 原子领取下一条提示，最大不超过 `hints` 长度，多标签页并发也不能重复领取或越界。
- 只返回本次新增提示及新计数；没有下一条时不增加计数。
- 已耗尽时返回 `200`、`hintIndex=null`、`hint=null`、`exhausted=true`；standard/free Session 返回 `409`；Session 不存在或不属于当前用户统一返回 `404`；请求体非法返回 `422`。
- 更新失败时前端不提前显示提示，应展示可重试错误。
- 页面恢复 Session 时，前端按 `revealedHintCount` 展示 `hints` 前缀。

## 8. UI 行为

主要定位线索：

- `web/src/components/practice/PracticeScenarioCard.jsx`
- `web/src/pages/PracticePage.jsx`
- `web/src/api/client.js`
- 对应 CSS、i18n 和测试文件

要求：

- `standard` 题继续执行当前“有 points 显示 points，否则显示 mission”的逻辑。
- `progressive_hints` 题初始总是显示 mission，不显示 points。
- 提示按钮只在已创建的渐进式 Session 中出现；待开始预览和 standard/free 模式不出现。
- 新提示出现在固定提示区域，不把录音主操作挤出视口，不触发整页自动滚动。
- 提示区域使用真实按钮语义，键盘可操作；新增提示应让读屏软件感知，但不能抢走录音按钮焦点。
- 移动端长文本换行后不横向溢出。
- 结果态、历史态和分享态不得新增提示使用标签。

## 9. 评分隔离

主要定位线索：

- `server/services/corrector.py`
- `server/routes/correct.py`
- `server/services/practice_attempts.py`

必须保证：

- standard 题继续使用当前 points 评分逻辑。
- progressive task 只把 `points` 作为必须信息传给 corrector。
- progressive chat/describe/opinion/explain 没有强制 points。
- `hints` 文本和 `hintCount` 永远不进入纠错或标准答案 Prompt。
- 相同 Scenario、相同 transcript、相同历史上下文，仅 `hintCount` 不同时，构造出的模型请求必须完全相同。
- 不能在结果文案中根据 `hintCount` 添加“你依赖了提示”等判断。

## 10. 试点题生成与质量门禁

### 10.1 数量与分布

首批固定生成 10 道公共题：

| kind | 数量 |
|---|---:|
| `task` | 2 |
| `chat` | 2 |
| `describe` | 2 |
| `opinion` | 2 |
| `explain` | 2 |

全部满足：

- `ownerUserId=null`
- `status=active`
- `interactionType=progressive_hints`
- 有唯一 slug、图片和现有分类坐标
- 进入正常题池，不做单独入口白名单

### 10.2 独立生成路径

渐进试点不得改变现有 standard 公共题自动补题语义。实现时建立独立、可复现的试点入口：

- 新增受版本控制的 `server/data/progressive_hint_pilot.yaml`，保存最终审核后的 10 道完整题目事实：slug、kind、category、difficulty、title、where、story、mission、points、hints、imagePrompt、videoPrompt。
- 新增专用脚本 `server/scripts/generate_progressive_hint_pilot.py`，只读取该 manifest，不让每次执行重新随机改写已审核文案。
- 脚本至少支持：
  - `--dry-run --ids <slug,...>`：校验并打印将要写入的数据，不调图片/视频服务、不写数据库；
  - `--execute --ids <slug,...>`：只处理显式指定且已通过校验的题；
  - `--archive --ids <slug,...>`：只把指定题改为 `archived`，输出修改前后状态。
- 每次付费生成/同步最多 5 道；10 道至少拆成两批。每批先 dry-run、人工审核，再执行图片和入库。
- slug 是 manifest 中的稳定主键；重复执行同一题必须幂等 upsert，不能制造第二道同 slug 题。
- 可复用现有图片、视频和 `sync_public_scenarios.py` 能力，但必须输出明确 scenarioId，且不能绕过人工审核直接写生产。
- 现有 `generate_scenarios.py`、`PUBLIC_GEN_PROMPT` 和 standard 自动 top-up 默认行为保持不变。若共享底层函数，validator 必须按 `interactionType` 分流，不能用 progressive 的空 points 规则放宽 standard。

manifest 的 10 组坐标由实现 Agent 在编码阶段从现有 taxonomy 中选择，必须满足五种 kind 各 2 道、难度有分布、与现有题不过度重复；最终坐标和文案以入库前人工审核记录为准。

### 10.3 生成语义

现有生成提示把 points 定义成“可直接照着说的中文话”，不能原样复用到渐进题。

渐进题生成必须区分：

- `story`：必要事实，不列举用户要说的句子。
- `mission`：宽泛沟通目标，单独看能知道要完成什么。
- `points`：仅 task 的评分条件，写成可检查的信息点。
- `hints`：按展示顺序给出的自然中文提示。
- `imagePrompt`：视觉上呈现核心场景或冲突，不能依赖图片中文字解释。

每条 hint 必须：

- 是完整中文句子；
- 与其他 hint 提供不同信息或推进；
- 不只是重复 mission；
- 不含英文、中英对照、整段范文或“可以说……”后的答案列表；
- 不使用“语气坚定”“展开讨论”等无法直接帮助开口的空泛指令。

### 10.4 硬规则

调整确定性 grader，使规则按 `interactionType` 分流：

- standard 题继续通过现有规则，不能因新字段而失败。
- progressive task：2–3 个非空 points、2–3 个 hints，数量一致。
- progressive 非 task：points 为空、2–3 个非空 hints。
- 五种 kind、字段长度、考试腔、emoji、近重复等现有规则继续适用。
- 10 道题硬规则通过率必须为 100%。

### 10.5 人工内容验收

生成不能以“JSON 合法”代替内容质量。投放前逐题检查：

- 不看 hints 时，审核者能说清地点/角色、发生了什么和沟通目标。
- 图片与 story 是同一场景，核心冲突可见；无字幕、水印和错误文字。
- mission 足够宽泛，不是一句可直接翻译的中文答案。
- hints 按顺序有增量，且最后一条也不是完整英文答案。
- task 的每个 point 都有对应 hint，且是完成任务真正必要的信息。
- 非 task 的 hints 只是展开支架，不被写进必答 points。
- 与现有生产题不是仅换地名、金额或角色名字的近重复。

任一项不通过就重生成或人工修订该题，不得以“只是试点”为由带病投放。

## 11. 遥测与隐私

与提示本身相关的数据只记录数量，不记录提示正文或用户如何使用提示；为去重和分层保留下面列出的不透明 ID 与场景标量。

### 11.1 持久数据

- Session：`revealedHintCount`
- Attempt：`hintCount`

### 11.2 现有 Umami 事件

扩展现有事件属性：

| 事件 | 新增属性 |
|---|---|
| `practice_recording_started` | `practiceId`、`sourceType`、`interactionType`、`kind`、`difficulty`、`hintCount` |
| `practice_result` | `practiceId`、`attemptId`、`sourceType`、`interactionType`、`kind`、`difficulty`、`hintCount` |

规则：

- `hintCount` 是事件发生时已显示的提示数。
- standard/free 统一上报 `0`。
- `practiceId`/`attemptId` 只用于事件去重；分析时按唯一 ID 计数，不能把网络重试当成多个用户行为。
- 不上报 hint 文本、story、mission、transcript、标准答案或 slug。
- 更新 `docs/业务/数据埋点.md`。
- 埋点失败继续遵循现有 Umami 静默策略，不能阻断练习；业务 Session/Attempt 的计数写入失败则必须明确失败，不能伪造成功。

## 12. 分阶段实施顺序

1. **契约与回归测试**
   - 先补 schema/归一化、standard 兼容和 grader 测试。
   - 用失败测试锁住“旧题不变”“提示不进评分”。
2. **后端业务路径**
   - Session 快照、原子 reveal、Attempt hintCount、exact slug API。
   - 完成权限、归档、并发上限和错误路径测试。
3. **前端交互**
   - URL 选题、渐进题卡、提示恢复、i18n、遥测。
   - 完成组件测试和 journey E2E。
4. **生成与评测**
   - 增加独立 manifest/脚本并改造确定性 grader，不改变 standard 自动生成路径。
   - 每批不超过 5 道；先 dry-run 并形成逐题审核表，不写生产。
5. **试点投放**
   - 生成并同步 10 道审核通过的题。
   - 逐个验证真实生产 URL、Session、Attempt、提示计数和历史。
6. **观察与决策**
   - 达到最小样本后按第 15 节判断继续、修改或归档。

## 13. 测试矩阵

| 层 | 必测场景 | 关键断言 |
|---|---|---|
| 后端单元 | interactionType 归一化 | 缺失/未知读为 standard；非法新写入失败 |
| 后端单元 | grader 分流 | standard 规则不变；task/非 task 契约分别生效 |

| 后端集成 | reveal | 逐次返回、同 requestId 重试结果相同、并发不重复、刷新可恢复 |

## 15. 试点验收：产品假设怎样算成功

### 15.1 最小观察样本

统计口径：

- 观察窗口从 PA-02 完成时间 `T0` 开始，至少持续 14 天；未达到样本下限则继续观察。
- 两组都排除 `sourceType=ai_test` 和 free 模式；progressive 组只取本批次 10 个 scenarioId，standard 对照组取同期其他 `interactionType=standard` 题。
- 统计单位是唯一 `practiceId`，不是 Attempt 数。每个 Session 只取第一个 completed Attempt 的 `hintCount`，重说不重复计入提示依赖率。
- standard 对照取同一窗口、相同 `kind + difficulty` 的唯一 Session；各层按 progressive 实际分布加权，不能用题量更大的类别淹没小类别。
- Umami 事件按 `practiceId`/`attemptId` 去重；`practice_result` 重发和同 Session 多轮录音不能被当成多个新用户。

至少满足以下样本后再判断：

- 上线满 14 天；
- 至少 30 个有 completed Attempt 的 progressive Session；
- 五种 kind 每种至少有 3 个 completed Session；
- matched standard 对照至少有 30 个开始录音的唯一 Session，且 progressive 出现的每个 `kind + difficulty` 层都有对照。

不满足样本条件时结论只能是“数据不足”，不能宣称成功或失败。

### 15.2 试点通过信号

以下是首轮决策阈值，不代表统计学证明：

| 指标 | 计算 | 通过线 |
|---|---|---:|
| 无提示完成率 | progressive Session 的首个 completed Attempt 中 `hintCount=0` 的比例 | `>= 50%` |
| 全提示依赖率 | progressive Session 的首个 completed Attempt 中 `hintCount=总 hints 数` 的比例 | `<= 35%` |
| 练习完成代理 | 唯一 `practice_result.practiceId` / 唯一 `practice_recording_started.practiceId` | 比 matched standard 低不超过 10 个百分点 |
| 技术可靠性 | reveal、exact slug、Session/Attempt 写入的服务端错误 | `0` 个未解决高优问题 |
| 评分隔离 | 因 hintCount 改变分数或反馈的已确认案例 | `0` |

全部满足：保留试点题，评审是否扩大渐进题数量。

未满足时：

- 全提示依赖率高：优先检查图片、story、mission 是否仍不够清楚，不直接增加更多提示。
- 完成代理明显下降：检查入口、按钮和错误路径；若体验本身造成阻塞，先归档试点题。
- 某一道题异常而整体正常：只归档该题，保留其他题继续观察。
- 发现作答前泄露英文答案、提示参与评分或错误 slug 建立了其他题的 Session：立即归档全部试点题，修复后重新验收。

## 17. 规格编写依据

截至本文编写时，没有找到 OpenAI 官方单独发布的“GPT-5.6 Prompting Guide”。官方模型页面确认 GPT-5.6 的存在，但不能据此杜撰 GPT-5.6 专属提示方法。因此本文使用的是官方 GPT-5、Codex 和 GitHub Coding Agent 指南的共同原则，而不是声称存在一份 GPT-5.6 模板。

主要参考：

- [OpenAI GPT-5 Prompting Guide](https://cookbook.openai.com/examples/gpt-5/gpt-5_prompting_guide)：明确任务、上下文、约束、工具规则和停止条件。
- [OpenAI Codex Prompting Guide](https://cookbook.openai.com/examples/gpt-5/codex_prompting_guide)：先调查仓库，再实现、测试并交付可审查结果。
- [OpenAI Codex ExecPlans](https://cookbook.openai.com/articles/codex_exec_plans)：计划应自包含、可由不了解历史的人执行，并写清里程碑、验证、恢复和证据。
- [OpenAI GPT-5.2 Prompting Guide](https://cookbook.openai.com/examples/gpt-5/gpt-5-2_prompting_guide)：接口字段、缺省值、错误和不确定性要显式，Prompt 变更应由 eval 驱动。
- [GitHub：Adding repository custom instructions](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)：给 Agent 提供仓库结构、工具、构建测试顺序、CI 与已知约束。
- [OpenAI GPT-5 model reference](https://help.openai.com/en/articles/9624314-gpt-5-models)：只用于确认模型信息，不作为 GPT-5.6 提示指南。

本文据此把聊天中的产品判断转换为：可观察用户结果、明确非目标、字段/API 契约、兼容与回退、分阶段实施、可执行测试、二元交付门禁、试点指标和最终证据。外部指南只决定“规格怎样写得可执行”，不替代 SpeakUp 自己的产品决策。
