# 运营通知：注册与练习提交合并推送飞书

- 状态：已完成
- 关联 PR：#206

## 背景与问题

线上有真实用户在用，但「谁注册了」「谁提交了练习」这类运营事件没有任何通知，只能主动翻数据库。

## 目标

- 新用户注册、用户提交练习（录音送评估）时推送到飞书。
- 10 分钟最多一条：窗口内的多条事件合并成一条消息，首条不延迟。
- 开关可配置，默认关闭；凭据只存 Infisical，不入库不进日志。

## 非目标

- 不做通知历史的管理界面（要查就看 `notificationEvents` 集合）。
- 不把用户内容（转写文本、AI 反馈、场景 story）推进 IM，只推谁做了什么。

## 方案权衡

| 决策点 | 选择 | 放弃的方案与理由 |
| --- | --- | --- |
| 事件采集 | 业务收口点直接入队（`_save_attempt_and_review`、登录新建用户分支） | 定时扫库：不用改业务代码，但要扫全表、延迟不可控 |
| 队列位置 | Mongo `notificationEvents` | 纯进程内队列：每次部署重启都会丢掉窗口内未发的事件 |
| 发送时机 | 首条立即发，窗口内攒到窗口结束合并 | 固定 10 分钟对齐窗口：第一条最多延迟 10 分钟 |
| 飞书通道 | 群自定义机器人 webhook | 复用已有 app 的 Open API 凭据：要把它多存一份到服务器，权限面更大（见 `common` 记忆里的既有结论） |
| 失败处理 | 保留 pending 下轮重试，超过 5 次标 failed | 丢弃或阻塞请求：前者丢通知，后者让通知影响登录和练习 |

## 决定

`server/services/notifier.py` 一个模块承载全部逻辑：`record_*` 入队、`flush_pending` 合并发送、`start_flusher` 由 lifespan 起后台任务。手机号在消息里脱敏为 `138****1234`；时间按北京时间渲染（生产机是 UTC）。`sourceType=ai_test` 的测试号不入队。

## 验收

- [x] 注册、练习提交各产生一条事件，`ai_test` 账号不产生。
- [x] 窗口内多条事件合并成一条消息；首条立即发出。
- [x] 关闭开关或未配 webhook 时全链路 no-op，不影响登录与评估。
- [x] 发送失败保留 pending 并计数重试，超限标 failed 不再堆积。
- [x] 日志与 `lastError` 不出现 webhook URL。
- [x] 本地跑通假接收器链路；生产上线后真发一条验证（见 changelog）。
