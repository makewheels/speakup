# Attempt 独立实体与对象存储重构

## 为什么要拆分

当前 `practiceSessions.attempts[]` 是嵌入数组，前端和 OSS 又使用数组下标或从 1 开始的轮次号定位资源。轮次号适合展示，不适合作为身份：数组迁移、修复、删除或并发写入后都可能改变位置，也无法让反馈、录音和分享稳定引用一次作答。

因此把职责拆开：

- `practiceSessions`：一道题/一个话题的会话容器，保存题目快照、模式、用户和创建时间。
- `practiceAttempts`：一次真实作答，保存原话、分数、gaps、标准答案、讲解、追问、录音资产及状态。

## 数据模型

```json
{
  "_id": "pa_1787576398044...",
  "practiceId": "ps_1787576398044...",
  "userId": "u_1786641842438...",
  "round": 1,
  "transcript": "...",
  "score": 6.5,
  "summary": "...",
  "gaps": [],
  "standardAnswer": "...",
  "standardAnswerNotes": [],
  "progress": null,
  "chat": [],
  "recording": {
    "id": "rec_...",
    "key": "practiceSessions/u_.../202608/ps_.../attempts/pa_.../recordings/rec_.../original.webm",
    "format": "webm",
    "contentType": "audio/webm;codecs=opus",
    "sizeBytes": 123456
  },
  "sourceType": "human",
  "createdAt": "...",
  "updatedAt": "..."
}
```

索引：

- `_id` 唯一；
- `(practiceId, round)` 唯一；
- `(userId, createdAt)`；
- 可选 `(practiceId, createdAt)`。

`round` 只用于“第几次尝试”的展示和排序。API、URL、对象存储、反馈关联全部使用 `attemptId`。

## API 过渡契约

- `GET /api/practice-sessions/{id}` 在迁移期继续返回 `attempts`，但内容来自 `practiceAttempts`；旧 session 没迁移时才回退嵌入数组。
- 每个返回 attempt 必须包含 `_id`/`attemptId`。
- 纠正写入在开始时预创建 Attempt，返回 `attemptId`，让前端立即进入 `?attempt=<pa_id>`；流完成后更新同一文档。
- 录音、TTS、追问、反馈接口接收 `attemptId`。旧 `attemptIndex` 只保留一个版本的兼容层，并在服务端解析到真实 ID。
- 分享页按 `practiceId` 取可公开的 Attempt 列表，并用 URL 中的 `attemptId` 精确打开被分享轮次；发音接口当前固定返回 410。

## OSS 路径

```text
practiceSessions/{userId}/{yyyyMM}/{practiceId}/attempts/{attemptId}/recordings/{recordingId}/original.{ext}
practiceSessions/{userId}/{yyyyMM}/{practiceId}/attempts/{attemptId}/speech/{purpose}/{speechId}.{ext}
```

月份仍取 session 的 `createdAt`。文件格式保留真实容器，浏览器录音不强制改成裸 PCM。

## 迁移策略

### audit

1. 扫描所有嵌入 attempt，为每项确定稳定 `pa_...` ID；可重复运行时必须读取已记录映射，不能每次生成新 ID。
2. 列出嵌入 attempt 数、已独立 attempt 数、冲突 `(practiceId, round)`、缺少用户或日期的数据。
3. 列出每个 recording/speech 源 key、目标 key、大小、ETag/CRC。
4. 只报告，不写数据库和 OSS。

### migrate

1. upsert `practiceAttempts`，保留原 `createdAt`、sourceType 和所有业务字段。
2. 同桶复制 OSS 对象到含 `attemptId` 的路径，逐对象校验。
3. 更新独立 Attempt 的资产 key。
4. session 写入迁移版本/完成标记；迁移期暂不删除嵌入数组。
5. API 双读验证通过后，新写只进入独立集合。

### cleanup

1. 再次核对独立 Attempt 数量和字段摘要。
2. 再次核对目标对象可读、大小与校验值。
3. 去除已迁移 session 的嵌入 attempts。
4. 删除已登记且数据库不再引用的旧 OSS 对象。
5. 对未关联对象逐项判断：能确认业务归属的迁移并补数据库引用；确认无引用、无业务用途的删除。最终报告不得留下无解释的错误路径或垃圾对象。

## 回滚边界

- cleanup 前可切回嵌入数组读取，旧对象仍在。
- cleanup 后回滚需要从独立集合重新组装嵌入结构，因此 cleanup 必须单独审批并保留迁移清单。
- 生产发布顺序必须是：双读代码 → audit → migrate → 新写切换 → 线上验证 → cleanup。

## 验收

- 同一 session 连续完成两轮，得到两个不同 `pa_` ID，round 分别为 1/2。
- 打开两个 `?attempt=<pa_id>` URL 分别还原对应结果，刷新不串轮。
- 每轮录音、TTS、反馈的数据库引用和 OSS 路径都包含对应 `pa_` ID。
- 迁移前后 API 返回的 attempt 数量、文本、分数、gaps 和录音可播放性一致。
- 并发或重复完成回调不会创建两个相同 `(practiceId, round)` 的 Attempt。
- cleanup 后数据库旧嵌入 attempt 数、错误 OSS 路径对象数、无用未引用对象数均为 0。
